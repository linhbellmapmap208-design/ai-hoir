# AGENTS.md — ai-hoir (TransKun transcription API)

## What this repo is
The repo originally contained only `requirements 2.txt` (TransKun's own dependency
list, nothing else — no source). The application in `app/` was authored on Base44:
a small FastAPI service that runs the **TransKun 2.0** piano-transcription model on
CPU and exposes it over HTTP for a bot to call. The stray `requirements 2.txt` is
superseded by `requirements.txt`; it is kept only because it was the uploaded file.

## Running it
```bash
docker compose -f docker-compose.base44.yml up -d --build    # first time / after dependency changes
docker compose -f docker-compose.base44.yml up -d            # normal start (source is bind-mounted)
docker compose -f docker-compose.base44.yml logs -f transcriber
```

- The container runs `uvicorn app.main:app --reload` on port 3000 with the repo
  bind-mounted at `/app`, so **code edits hot-reload**. Rebuild only when
  `requirements.txt` or `Dockerfile.base44` change.
- `WATCHFILES_FORCE_POLLING=true` is set because the source arrives through a bind mount.

## Non-obvious things worth knowing
- **No model download.** The TransKun 2.0 checkpoint (`pretrained/2.0.pt`, ~56 MB) and
  its config (`pretrained/2.0.conf`) ship **inside the pip package**. `transkun`
  is pinned to `2.0.1`.
- **torch must be the CPU wheel.** `Dockerfile.base44` installs `torch`/`torchaudio`
  from `https://download.pytorch.org/whl/cpu` *before* `pip install -r requirements.txt`,
  so transkun's unpinned torch dependency is already satisfied and no CUDA wheels
  (~2 GB) are pulled.
- `numpy<2` is pinned on purpose — `pretty-midi` / `mir-eval` are happiest there.
- **Model loading is asynchronous.** `app/transcriber.py` loads the checkpoint in a
  daemon thread at startup so uvicorn can bind immediately. `/health` reports
  `loading` → `ready` (or `error` with the failure message). `/transcribe` waits up to
  600 s for the load and returns 503 if it failed.
- **Audio decoding:** everything goes through ffmpeg via pydub, is downmixed to mono,
  and is resampled to the model's 44.1 kHz with `soxr`. TransKun expects a
  `(frames, channels)` tensor, so mono input needs an explicit trailing axis
  (`samples[:, None]`) — passing a 1-D array breaks its internal `x[:, i:j]` slicing.
- **MIDI channel:** `pretty_midi.Instrument` has *no* `.channel` attribute. The channel
  written by `writeMidi()` is read back from the generated bytes with `mido`
  (`_midi_channels`). TransKun emits a single piano instrument, so it is channel 0.
- **CPU inference is slow** — roughly real-time-ish per minute of audio on 4 cores;
  a full song takes minutes. That is expected, not a hang. The healthcheck uses a
  short timeout but does not kill the container.

## API
- `POST /transcribe` — multipart field `file` → `audio/midi`; channel in the
  `X-Midi-Channel` header, note count in `X-Note-Count`.
- `POST /transcribe?format=json[&include_notes=true]` — JSON with `midi_base64`,
  `channel`, `note_count` (and per-note `channel` when `include_notes=true`).
- `GET /health`, `GET /docs`, `GET /` (landing page showing the public bot link).

## How to verify it works
```bash
curl -s http://localhost:3000/health          # expect "status":"ready"
curl -F "file=@song.mp3" http://localhost:3000/transcribe -o out.mid   # expect an MThd MIDI file
```
`out.mid` should start with the bytes `MThd`. A quick synthetic-audio smoke test
(a few notes, ~2 s) transcribes in a few seconds; longer files take proportionally longer.
